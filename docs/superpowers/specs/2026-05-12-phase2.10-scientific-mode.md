# Phase 2.10 — Scientific Mode + Memory Functions + Landscape Adaptive Layout

> **Status:** Design contract. Brainstorm at `docs/explore/phase2.10-scientific-mode.html` is the source of design exploration; this document is the locked, executable distillation.

**Branch:** `feature/phase2.10-scientific-mode` (off `development` at `7b2f344`)
**Date:** 2026-05-12
**Plan:** `docs/superpowers/plans/2026-05-12-phase2.10-scientific-mode.md`

---

## 1 · Goal

Extend the basic calculator into a scientific calculator with:

- A toggleable **scientific mode** (trig, log/ln, e^x, π/e, x², √, x^y, x!).
- The four classic **memory keys** (MC, M+, M−, MR).
- An adaptive **landscape layout** that exposes both basic and scientific blocks side-by-side without manual mode switching.

The implementation is **additive** — the existing parser, evaluator, MVI state, and DI graph (all hardened in Phases 2.2–2.9) are extended, not replaced.

---

## 2 · Scope

### In scope

- Toolbar toggle (🧪) between Basic and Scientific modes; mode persisted to DataStore.
- Scientific operations:
  - **Trig:** `sin`, `cos`, `tan`, `asin`, `acos`, `atan`
  - **Logs / exp:** `ln`, `log` (base 10), `exp`
  - **Powers / roots:** `x²` (via `^2`), `x^y` (right-associative), `√` (`sqrt`)
  - **Factorial:** `x!` (integers ≥ 0)
  - **Constants:** `π`, `e`
  - **Angle unit:** `deg` / `rad` toggle, default **degrees**
- Memory: `MC` (clear), `M+` (add), `M−` (subtract), `MR` (recall). Memory row always visible in both modes.
- `M` chip in toolbar when memory is non-null.
- Landscape adaptive layout via `WindowSizeClass`: display spans top, scientific block left, basic block right (iOS-style); memory row sits at top of basic block.
- RTL mirroring of block order under `LayoutDirection.Rtl` in landscape.
- Arabic copy for every new string.
- `@Preview` coverage for both modes (portrait + landscape) and the typical state-machine states.
- Tests for every new parser token, evaluator operation, memory flow, and config-change preservation.

### Out of scope

- Tip calc, unit conversions, NL parsing, custom formulas (separate phases).
- Tablet/large-screen layout beyond what `WindowSizeClass` gives us for free.
- Graph plotting, symbolic math, complex numbers.
- History rows showing scientific function names (basic display still wins; revisit later).
- New theme picker (parked in `project_phase2_backlog.md`).
- Implicit multiplication — `2π` will not parse; users must type `2×π`.
- Factorial extension via Γ(n+1) — integers ≥ 0 only; domain error otherwise.

## 3 · Operations matrix

| Op | Syntax in expression | Parser change | Evaluator change | Risk |
|---|---|---|---|---|
| `sin`, `cos`, `tan` | `sin(x)` | `Function("sin")` token | New `evalPrimary` function branch | Low |
| `asin`, `acos`, `atan` | `asin(x)` | Same as trig | Same; domain-checked | Low |
| `ln` | `ln(x)` | Same | Domain-checked (`x > 0`) | Low |
| `log` (base 10) | `log(x)` | Same | Domain-checked (`x > 0`) | Low |
| `exp` (e^x) | `exp(x)` | Same | Same | Low |
| `sqrt` (√) | `sqrt(x)` | Same | Domain-checked (`x ≥ 0`) | Low |
| `π`, `e` | `π`, `e` | `Constant("pi")` / `Constant("e")` | New `evalPrimary` constant branch | Low |
| `x²` (square) | written as `x^2` | Reuse `^` | Reuse `evalPower` | Low |
| `x^y` (power) | `x^y` | New `Operation.POWER` (`'^'`) | New `evalPower` tier — right-associative | Med (precedence) |
| `x!` (factorial) | `x!` | `Postfix(FACTORIAL)` token | New `evalPostfix` — integers ≥ 0 | Med (postfix grammar) |
| `deg/rad` | (mode state) | None | Wrap trig args in conversion | Low |

The only two non-trivial grammar additions are `^` (right-associative, precedence between `×÷%` and unary) and `!` (postfix unary, highest precedence after grouping). Everything else slots into the existing recursive-descent grammar by adding a `function` production and a `constant` production at the primary tier.

## 4 · Parser grammar (additive)

Current grammar (`ExpressionEvaluator.kt:3-8`):

```
expression → term (± term)*
term       → factor (×|÷|% factor)*
factor     → number | (expression) | ±factor
```

Extended grammar:

```
expression → term (± term)*
term       → power (×|÷|% power)*
power      → unary (^ power)?            ← new, right-associative
unary      → ±unary | postfix
postfix    → primary (!)*                ← new, factorial (chainable)
primary    → number | constant | function | (expression)
function   → name "(" expression ")"     ← sin, cos, ln, log, sqrt, exp, …
constant   → "π" | "e"
```

**Precedence (lowest → highest):**

1. `+`, `-` (binary)
2. `×`, `÷`, `%`
3. `^` (right-associative)
4. unary `+`, `-`
5. `!` (postfix)
6. primary (number / constant / function / parenthesised)

Right-associativity for `^`: `2^3^2` evaluates to `2^(3^2) = 512`, not `(2^3)^2 = 64`.

### `ExpressionPart` additions

```kotlin
sealed interface ExpressionPart {
    data class Number(val number: Double) : ExpressionPart                 // existing
    data class Op(val operator: Operation) : ExpressionPart                // existing
    data class Parentheses(val type: ParenthesesType) : ExpressionPart     // existing
    data class Function(val name: String) : ExpressionPart                 // NEW
    data class Constant(val name: ConstantSymbol) : ExpressionPart         // NEW
    data class Postfix(val op: PostfixOp) : ExpressionPart                 // NEW
}

enum class ConstantSymbol(val symbol: Char, val value: Double) {
    PI('π', kotlin.math.PI),
    E('e',  kotlin.math.E),
}

enum class PostfixOp(val symbol: Char) {
    FACTORIAL('!'),
}
```

`Operation` enum gains `POWER('^')`. The existing `operationSymbols` aggregator (`Operation.kt:11`) automatically picks it up, so `ExpressionWriter`'s char-membership checks (`canEnterOperation`, `prepareForCalculation`) continue to work.

### Parser tokenisation rules

| Char(s) at index `i` | Token emitted |
|---|---|
| Digit `0–9` (optionally with `.` and `E`±digits trailing) | `Number` (existing) |
| `+ - x / % ^` | `Op(operationFromSymbol(c))` |
| `(` `)` | `Parentheses(Opening|Closing)` |
| `!` | `Postfix(FACTORIAL)` |
| `π` | `Constant(PI)` |
| `e` **when not part of a number** | `Constant(E)` |
| ASCII letter sequence followed by `(` | `Function(name)` — name is lowercase identifier; `(` is then consumed as a separate `Parentheses(Opening)` token on the next iteration |

`e` is ambiguous with scientific-notation exponents. The existing `parseNumber` (`ExpressionParser.kt:45-58`) consumes `E`/`e` only when it follows a digit run AND is followed by `[+-]?digit+`. Standalone `e` (no preceding digit, or no following exponent-digit pattern) falls through to the function/constant tokenizer.

### Evaluator dispatch

`evalPrimary(parts)` dispatches on the first token:

- `Number(n)` → `n`
- `Constant(c)` → `c.value`
- `Function(name)` → consume next opening `(`, recurse into `evalExpression`, consume closing `)`, apply `dispatchFunction(name, inner, angleUnit)`. Throws `CalcError.DomainError` for `sqrt(-1)`, `log(≤0)`, `ln(≤0)`, `asin(|x|>1)`, `acos(|x|>1)`, etc.
- `Parentheses(Opening)` → recurse into `evalExpression`, drop closing `)` (existing behavior).
- Anything else → `CalcError.SyntaxError`.

`evalPostfix(parts)` runs `evalPrimary` then while the next token is `Postfix(FACTORIAL)` applies factorial. Factorial of non-integers or negative numbers throws `CalcError.DomainError`. Factorial of any `n > 170` throws `CalcError.Overflow` (170! is the last value representable in `Double`).

`evalPower(parts)` runs `evalUnary` then if the next token is `Op(POWER)` recurses right (`a^(power-tail)`).

### Angle-unit handling

`AngleUnit ∈ { Degrees, Radians }`. Default: **Degrees** (consumer-calculator convention; Samsung/iOS).

```kotlin
private fun toRadians(x: Double): Double =
    if (angleUnit == AngleUnit.Degrees) x * Math.PI / 180.0 else x

private fun fromRadians(x: Double): Double =
    if (angleUnit == AngleUnit.Degrees) x * 180.0 / Math.PI else x
```

Forward trig (`sin`, `cos`, `tan`) wraps the input via `toRadians`. Inverse trig (`asin`, `acos`, `atan`) wraps the output via `fromRadians`.

## 5 · State model

```kotlin
data class CalculatorState(
    val expression: String = "",
    val cursor: Int = 0,
    val selectionStart: Int = 0,
    val livePreview: String? = null,
    val error: UiText? = null,
    val mode: CalculatorMode = CalculatorMode.Basic,        // NEW
    val angleUnit: AngleUnit = AngleUnit.Degrees,           // NEW
    val memoryValue: Double? = null,                         // NEW
)

enum class CalculatorMode { Basic, Scientific }
enum class AngleUnit { Degrees, Radians }
```

`memoryValue` is `null` when cleared. Any non-null value (including `0.0`) lights the `M` chip in the toolbar.

### `CalculatorAction` additions

```kotlin
sealed interface CalculatorAction {
    // existing …
    data class Function(val name: String) : CalculatorAction        // NEW — sin, cos, ln, etc.
    data class Constant(val symbol: ConstantSymbol) : CalculatorAction  // NEW — π, e
    data object Factorial : CalculatorAction                          // NEW
    // Power is just Op(Operation.POWER) — no new action needed.
    data object ToggleMode : CalculatorAction                         // NEW
    data object ToggleAngleUnit : CalculatorAction                    // NEW
    data object MemoryClear : CalculatorAction                        // NEW — MC
    data object MemoryAdd : CalculatorAction                          // NEW — M+
    data object MemorySubtract : CalculatorAction                     // NEW — M−
    data object MemoryRecall : CalculatorAction                       // NEW — MR
}
```

`Function`, `Constant`, `Factorial` go through `ExpressionWriter`, which inserts the correct character(s) at the cursor (e.g. `Function("sin")` inserts `"sin("` and advances the cursor inside the parens).

`ToggleMode` and `ToggleAngleUnit` go through `SettingsRepository` (DataStore-backed).

`MemoryAdd` / `MemorySubtract` evaluate the current expression via `writer.tryEvaluate()`; on success they update `memoryValue`; on error they emit `FeedbackIntent.Error` and leave memory unchanged.

`MemoryRecall` inserts the current `memoryValue` as a number literal at the cursor (no-op when `memoryValue == null`).

## 7 · Error handling

`CalcError` (`feature/calculator/domain/CalcError.kt`) currently has two entries: `DIVISION_BY_ZERO`, `INVALID_EXPRESSION`. It gains:

```kotlin
enum class CalcError : Error {
    DIVISION_BY_ZERO,
    INVALID_EXPRESSION,
    DOMAIN_ERROR,    // NEW — log(0), sqrt(-1), asin(2), 0!=1 stays valid
    OVERFLOW,        // NEW — 200!, factorial above 170
    SYNTAX_ERROR,    // NEW — unbalanced function parens, "sin)"
}
```

`CalcErrorMapper.kt` maps each to a `UiText.StringResource`:

| Enum | String key | EN | AR |
|---|---|---|---|
| `DOMAIN_ERROR` | `calc_error_domain` | "Outside function domain" | "خارج نطاق الدالة" |
| `OVERFLOW` | `calc_error_overflow` | "Number too large" | "الرقم كبير جدًا" |
| `SYNTAX_ERROR` | `calc_error_syntax` | "Check the expression" | "تحقق من الصيغة" |

Existing `INVALID_EXPRESSION` is retained as the catch-all for parser failures that don't fit a more specific category.

## 8 · Layout decisions

### Portrait — Layout A (toggle in toolbar + expanded keypad)

```
┌─ Sifr ──────── [⚙] [📜] [🧪]┐
│       12 × sin(45) + π     │   ← display
│              = 12.500…     │
├────────────────────────────┤
│ sin  cos  tan  ln    log   │   ← scientific row 1 (Scientific mode only)
│ x²   √    x^y  x!    π/e   │   ← scientific row 2 (Scientific mode only)
│ asin acos atan exp   deg   │   ← scientific row 3 (Scientific mode only)
│ MC   M+   M−   MR    ()    │   ← memory row (BOTH modes)
├────────────────────────────┤
│ AC   ⌫    %    ÷           │
│ 7    8    9    ×           │
│ 4    5    6    −           │
│ 1    2    3    +           │
│ +/−  0    .    =           │
└────────────────────────────┘
```

- The `🧪` toolbar button toggles `Basic ↔ Scientific`.
- In Basic mode, the three scientific rows are hidden; the memory row is still visible.
- In Scientific mode, all three scientific rows are visible.
- The `deg` button (bottom-right of scientific row 3) toggles `Degrees ↔ Radians`; it shows the **current** unit, so it reads `deg` in Degrees mode and `rad` in Radians mode.
- `π/e` is a single cell that, on tap, inserts `π`; long-press inserts `e`. (Implementation: dedicated `CalculatorUiAction` with a long-press callback; see Plan Task 5.)

### Landscape — Layout A-Land (restructured, iOS-style)

```
┌─ Sifr ───────────────────────────────── [⚙] [📜] [🧪] ─┐
│                                                        │
│        12 × sin(45) + π        = 12.500…               │
│                                                        │
├────────────────────────────────┬───────────────────────┤
│ sin  cos  tan  asin acos atan  │  MC  M+  M−  MR       │
│ ln   log  exp  x²   √    x^y   │  AC  ⌫   %    ÷       │
│ π    e    x!   (    )    deg   │  7   8   9    ×       │
│                                │  4   5   6    −       │
│                                │  1   2   3    +       │
│                                │  +/− 0   .    =       │
└────────────────────────────────┴───────────────────────┘
        ◀── scientific block ──▶   ◀── basic block ──▶
```

- Display spans full width.
- Scientific block is **always visible** in landscape — landscape "earns" Scientific mode for free.
- Memory row sits at the **top** of the basic block (symmetric with portrait M1 placement).
- Toolbar toggle (🧪) still applies — but in landscape, even when `mode = Basic`, the scientific block remains visible (rotation is opportunistic, not a forced mode change). The toggle then primarily controls portrait visibility; flipping back to portrait honors the persisted mode.

### Adaptive driver

- **`WindowSizeClass.widthSizeClass`** is the trigger, not raw orientation. Compact width → portrait layout; Medium/Expanded width → landscape layout.
- Justification: future-proofs for tablets, foldables, and split-screen. Orientation is a poor proxy for "do I have horizontal space?".
- Drive via `androidx.compose.material3.windowsizeclass.calculateWindowSizeClass(activity)` (already a dependency at `app/build.gradle.kts:138`; no plumbing required).

### RTL

- Numbers in the display are LTR-anchored (per Phase 2.8 behavior — `CalculatorDisplay` already handles this).
- In **portrait**, button grid order is unchanged in RTL — calculator keypads are typically LTR even in Arabic locales.
- In **landscape**, block order is mirrored under `LayoutDirection.Rtl`: basic block on the left, scientific block on the right.

### Configuration change

- Rely on default `Activity` recreation + `SavedStateHandle` (already wired in Phase 2.9). No `android:configChanges` manifest hack.
- `WindowSizeClass` recalculates on recreate; layout swap is transparent.
- `mode`, `angleUnit` come from DataStore (cold-start hydrated via `SettingsRepository.observe()`).
- `memoryValue`, `expression`, `cursor`, `selectionStart` come from `SavedStateHandle`.

## 9 · UI surface — `CalculatorActions`

`CalculatorActions.kt` (currently a single flat `val calculatorActions: List<CalculatorUiAction>` at lines 10–117) is restructured into named rows:

```kotlin
val basicRows: List<List<CalculatorUiAction>>      // existing 5 rows
val scientificRows: List<List<CalculatorUiAction>> // new: 3 rows × 6 columns
val memoryRow: List<CalculatorUiAction>            // new: 4 keys + () + spacer
```

The grid composable becomes mode-aware:

```kotlin
@Composable
fun CalculatorButtonGrid(
    mode: CalculatorMode,
    memoryActive: Boolean,
    onAction: (CalculatorAction) -> Unit,
    modifier: Modifier = Modifier,
) {
    val rows = buildList {
        if (mode == CalculatorMode.Scientific) addAll(scientificRows)
        add(memoryRow)
        addAll(basicRows)
    }
    LazyVerticalGrid(columns = GridCells.Fixed(...), …)
}
```

In landscape (`A-Land`), the grid is split into two side-by-side columns rather than reflowed — see `CalculatorScreenLandscape` composable in the plan.

### `HighlightLevel` mapping for new keys

| Key class | HighlightLevel | Rationale |
|---|---|---|
| `sin`, `cos`, `ln`, `log`, etc. (function keys) | `Neutral` | Same visual weight as digits — these are "primary input" keys |
| `π`, `e`, `√`, `x²`, `x^y`, `x!`, `(`, `)` | `Neutral` | Same |
| `deg/rad` toggle | `SemiHighlighted` | Toggles a mode, like operators |
| `MC`, `M+`, `M−`, `MR` | `SemiHighlighted` | Memory keys behave like utility operators |
| `🧪` toolbar toggle | (icon-only, in app bar) | Outside the grid |

## 11 · Acceptance criteria

A reviewer should be able to verify the phase is "done" by:

1. **Mode toggle:** Tap 🧪 → scientific rows appear; tap again → they disappear. Toggle survives process kill (relaunch shows same mode).
2. **Scientific ops:** With degrees, `sin(30) =` shows `0.5`. With radians (toggle `deg → rad`), `sin(π) =` shows `≈0` (within `1e-10`).
3. **Power:** `2^3^2 =` shows `512` (right-associative).
4. **Factorial:** `5! =` shows `120`. `200! =` shows the overflow error string.
5. **Memory:** Type `5+3 =`, tap `M+`. Memory chip lights up. Clear, type nothing, tap `MR` → `8` appears in the expression. Tap `MC` → chip goes dark.
6. **Memory persistence:** Set memory, kill process via adb (`adb shell am kill com.gaddal.materialcalculator`), relaunch → memory chip still on, MR still recalls value.
7. **Landscape:** Rotate to landscape → display spans full width, scientific block visible on the left, basic block on the right. Memory row at top of basic block. Rotation does **not** change the persisted `mode` setting (verified by rotating back to portrait, which honors the original setting).
8. **RTL:** Switch device locale to Arabic → in landscape, basic block moves to the left, scientific block to the right. New error strings render in Arabic.
9. **Previews:** Android Studio preview pane shows all 6 `CalculatorScreen` previews + 4 grid previews. The typical-success preview also renders in light/dark and at all `@PreviewScreenSizes` slots.
10. **Tests pass:** `./gradlew :app:testDebugUnitTest` is green. New tests cover every new parser token, evaluator op, memory action, and config-change preservation. Lint baseline stays at 0/5.
