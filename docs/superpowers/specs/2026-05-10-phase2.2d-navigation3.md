## 1. Context & Goals

Phase 2.2c put Koin in charge of constructing `CalculatorViewModel`. `MainActivity` calls `CalculatorRoot()` directly — there's no nav layer. Phase 2.2d inserts Navigation 3 between them so Phase 2.3 can add a Settings destination without re-architecting the activity.

After this phase:

- **Navigation 3 1.1.1** is on the classpath (`androidx.navigation3:navigation3-runtime` + `navigation3-ui`). Nav3 hit GA at 1.0.0; current stable is 1.1.1.
- A `navigation/Routes.kt` declares the typed route surface — initially `data object CalculatorRoute : NavKey`.
- A `navigation/NavRoot.kt` composable owns the back stack via `remember { NavBackStack<NavKey>(CalculatorRoute) }`, hosts `NavDisplay`, and dispatches via the `entryProvider { entry<CalculatorRoute> { CalculatorRoot() } }` DSL.
- `MainActivity.setContent { SifrTheme { NavRoot() } }` — no direct `CalculatorRoot()` call from the activity.

User-visible behavior is identical. There is no second screen yet — Calculator is the only destination. Nav3 is wired so Phase 2.3 (settings) can add a route in a single small commit instead of an architectural change.

### Why Navigation 3 (and not staying on direct composable invocation)

The greenfield spec section 2 locks Nav3 as the navigation choice. Wiring it now (with one destination) is a 50-line change; wiring it later (alongside settings) bundles two concerns in one PR. Per the umbrella spec section 2 ordering rationale: "2.2c before 2.2d because Nav3's `NavRoot` is the natural place to host top-level Koin scope". The Application class is already wired in 2.2c, so the Koin scope is in place — what's left is the back-stack host.

### Why skip `koin-compose-navigation3` and `navigation3-adaptive`

- **`koin-compose-navigation3`** provides the modular `navigation<Route> { ... }` Koin DSL and `getEntryProvider()` walker. It pays off when there are multiple feature modules each owning their destinations. With one destination today, it's overhead. Add when Phase 2.3 brings `feature/settings/di/settingsModule.kt` and the modular pattern starts to earn its keep.
- **`navigation3-adaptive`** provides `ListDetailSceneStrategy`, `TwoPaneSceneStrategy`, etc. No multi-pane layout exists yet; the calculator is a single-screen app on phone form factor. Add when a feature actually needs adaptive panes.

### Why no `@Serializable` on `CalculatorRoute`

`rememberNavBackStack(CalculatorRoute)` is the canonical Nav3 idiom — it wraps `rememberSaveable` so the back stack survives configuration change and process death. That requires every `NavKey` to be `@Serializable` (which in turn requires the kotlinx-serialization plugin + runtime).

For Phase 2.2d's scope (single route, back stack always `[CalculatorRoute]`), state restoration is meaningless — the stack is reconstructed to the same single value on rotation. Using `remember { NavBackStack<NavKey>(CalculatorRoute) }` is genuinely simpler, requires no serialization plumbing, and behaves identically end-to-end.

When Phase 2.3 adds a real second destination, that's the moment to:
1. Add the kotlinx-serialization plugin + runtime.
2. Annotate every `NavKey` with `@Serializable`.
3. Switch to `rememberNavBackStack(CalculatorRoute)` for proper state restoration.

This is YAGNI in action — defer the serialization apparatus until there's a back-stack state worth preserving.

### Out of scope (deferred)

- **A second destination** (`SettingsRoute`) — Phase 2.3.
- **`koin-compose-navigation3`** + the modular `navigation<Route> { ... }` DSL — Phase 2.3 (when the modular graph earns its keep).
- **kotlinx-serialization** + `@Serializable` on routes + `rememberNavBackStack` — Phase 2.3 (when state restoration matters).
- **`navigation3-adaptive`** + `SceneStrategy` (list-detail / two-pane / dialog) — when a feature needs them.
- **`dropUnlessResumed`** wrapping on click handlers — Phase 2.3 (when there are real navigation clicks; today's only event is system back, which `NavDisplay` handles internally).
- **Deep links** — Phase 2.3+ (no URI surface yet).
- **Tests for `NavRoot`** — Compose UI test through `MainActivity` already exercises the calculator buttons end-to-end via `CalculatorScreenTest`. Once `NavRoot` hosts the calculator, that test still validates the user-visible flow. A separate `NavRootTest` is YAGNI for a single-destination graph.

### 2.4 `app/src/main/java/dev/gaddal/sifr/navigation/NavRoot.kt` (NEW)

```kotlin
package dev.gaddal.sifr.navigation

import androidx.compose.runtime.Composable
import androidx.compose.runtime.remember
import androidx.navigation3.runtime.NavBackStack
import androidx.navigation3.runtime.NavKey
import androidx.navigation3.runtime.entry
import androidx.navigation3.runtime.entryProvider
import androidx.navigation3.ui.NavDisplay
import dev.gaddal.sifr.feature.calculator.ui.CalculatorRoot

@Composable
fun NavRoot() {
    val backStack = remember { NavBackStack<NavKey>(CalculatorRoute) }
    NavDisplay(
        backStack = backStack,
        onBack = { keysToRemove -> repeat(keysToRemove) { backStack.removeLastOrNull() } },
        entryProvider = entryProvider {
            entry<CalculatorRoute> { CalculatorRoot() }
        },
    )
}
```

Notes:
- `remember { NavBackStack<NavKey>(CalculatorRoute) }` — no `rememberSaveable` (see spec section 1 on why).
- `onBack` receives a `keysToRemove: Int` parameter (Nav3 1.1+ predictive back support); for our single-destination app, the system back press still defers to OS handling because `backStack.removeLastOrNull()` on a one-element stack returns null and the activity finishes.
- `entryProvider { entry<CalculatorRoute> { CalculatorRoot() } }` — the DSL form (cleaner than a `when` over `key`).
