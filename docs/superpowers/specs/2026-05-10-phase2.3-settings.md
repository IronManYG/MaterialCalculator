## 1. Context & Goals

Phase 2.2 closed the architecture migration — Koin DI, MVI on Calculator, Navigation 3 in place. Phase 2.3 ships the **first user-visible feature beyond Calculator**: a Settings screen that persists user preferences (theme mode, haptics toggle, sound toggle) to DataStore Preferences and applies the theme choice to the app immediately.

After this phase, the user can:

1. Tap a settings icon on the calculator screen.
2. Land on a Settings screen with three controls: a theme picker (System / Light / Dark), a haptics switch, a sound switch.
3. Change theme — the app re-themes immediately on both Settings and Calculator screens.
4. Toggle haptics or sound — values persist (no actual feedback execution yet; that lands as a follow-up polish).
5. Press back (system or top-app-bar arrow) to return to Calculator.
6. Restart the app — all settings persist.

### What changes architecturally

This phase brings several "first time" patterns to the codebase:

- **First data layer.** `core/data/settings/SettingsRepository` (interface) + `feature/settings/data/SettingsRepositoryImpl` (DataStore-backed). Establishes the data-layer split per `android-data-layer` skill.
- **First DataStore.** `androidx.datastore:datastore-preferences` for the `themeMode` / `hapticsEnabled` / `soundEnabled` triple.
- **First domain models.** `core/domain/settings/AppSettings` + `ThemeMode`. Pure Kotlin, no Android imports — KMP-reachable per greenfield spec section 2.2.
- **First `coreDataModule`.** Koin module for the DataStore singleton; `feature/settings/di/settingsModule` consumes it for the repository binding.
- **First second nav destination.** `SettingsRoute : NavKey` joins `CalculatorRoute`. This forces the kotlinx-serialization plumbing the 2.2d spec deferred:
  - kotlinx-serialization Kotlin compiler plugin (`org.jetbrains.kotlin.plugin.serialization`)
  - `kotlinx-serialization-core` runtime
  - `@Serializable` annotations on every `NavKey`
  - `rememberNavBackStack(...)` instead of `remember { NavBackStack(...) }` for back-stack state restoration
- **First MVI events channel.** Phase 2.2b's spec deferred the `CalculatorEvent` channel until "the first real event" arrives. Phase 2.3 brings it: `CalculatorEvent.NavigateToSettings`. This pulls in:
  - `core/ui/util/ObserveAsEvents.kt` — `@Composable fun <T> ObserveAsEvents(events: Flow<T>, onEvent: (T) -> Unit)`
  - A `Channel<CalculatorEvent>` in `CalculatorViewModel`
  - `dropUnlessResumed { ... }` wrapping on the navigation click handler (per `android-navigation-3` skill)
- **First MVI events for a new feature.** `SettingsAction` + `SettingsEvent` + Settings ViewModel emitting `NavigateBack` follow the same pattern.
- **First theme parameterization.** `SifrTheme(themeMode: ThemeMode = ThemeMode.System, ...)` resolves `darkTheme: Boolean` from the mode (System honors `isSystemInDarkTheme()`; Light/Dark override).

### Out of scope (deferred)

- **Actual haptic feedback execution** (`HapticController` injecting and firing on calculator key presses). Toggle persists but doesn't yet drive a real effect. Polish task.
- **Actual sound execution** (`SoundController` + sound assets). Same as haptics.
- **Arabic string resources for Settings.** Settings UI uses `R.string.*` resources from day one (so Phase 2.5 is a translation pass, not a refactor pass), but only English strings ship now. `values-ar/strings.xml` updates in Phase 2.5 alongside the existing calculator strings.
- **Theme rename `SifrTheme` → `AppTheme`** per greenfield spec section 3.4. Keep `SifrTheme` for now; rename rides with a future theme-system expansion phase.
- **Dynamic-color toggle in Settings.** Greenfield spec doesn't surface this as a user setting; current `SifrTheme(dynamicColor = true)` default stays. Could become a setting later; not now.
- **Settings-side error UI.** Per greenfield spec section 5.5 ("Settings & History — silent best-effort"), DataStore IO failures fall back to defaults silently (the `IOException` → `emptyPreferences()` pattern). No `UiText` / error banner on Settings.
- **`koin-compose-navigation3`** modular DSL. Single `NavRoot` with two entries doesn't earn the modular pattern yet. Add when Phase 2.4's history feature brings the third destination — that's three modules and the modular DSL becomes worthwhile.
- **Settings icon's exact visual treatment.** Phase 2.3 ships a minimal `IconButton` overlay on the calculator display (aligned top-end). A proper `TopAppBar` on Calculator is its own design conversation; out of scope.

### 2.4 Repository (interface in `core/`, impl in `feature/settings/data/`)

#### `core/data/settings/SettingsRepository.kt`

```kotlin

import kotlinx.coroutines.flow.Flow

interface SettingsRepository {
    fun observe(): Flow<AppSettings>

}
```

The interface lives in `core/data/` because both `feature/calculator/` (read-only — observes `themeMode` for theme app-wide) and `feature/settings/` (read+write) consume it. Per greenfield spec section 2.2 promotion rule: "promoted to `core/` only when **two or more features** touch it" — Settings + Calculator + MainActivity all touch it.

#### `feature/settings/data/SettingsRepositoryImpl.kt`

```kotlin
package dev.gaddal.sifr.feature.settings.data

import androidx.datastore.core.DataStore
import androidx.datastore.preferences.core.Preferences
import androidx.datastore.preferences.core.booleanPreferencesKey
import androidx.datastore.preferences.core.edit
import androidx.datastore.preferences.core.emptyPreferences
import androidx.datastore.preferences.core.stringPreferencesKey
import dev.gaddal.sifr.core.data.settings.SettingsRepository
import dev.gaddal.sifr.core.domain.settings.AppSettings
import dev.gaddal.sifr.core.domain.settings.ThemeMode
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch
import kotlinx.coroutines.flow.map
import java.io.IOException

class SettingsRepositoryImpl(
    private val dataStore: DataStore<Preferences>,
) : SettingsRepository {

    override fun observe(): Flow<AppSettings> = dataStore.data
        .catch { e -> if (e is IOException) emit(emptyPreferences()) else throw e }
        .map { it.toAppSettings() }

    override suspend fun update(transform: AppSettings.() -> AppSettings) {
        dataStore.edit { prefs ->
            val current = prefs.toAppSettings()
            val updated = current.transform()
            prefs[KEY_THEME_MODE] = updated.themeMode.name
            prefs[KEY_HAPTICS] = updated.hapticsEnabled
            prefs[KEY_SOUND] = updated.soundEnabled
        }
    }

    private fun Preferences.toAppSettings(): AppSettings = AppSettings(
        themeMode = this[KEY_THEME_MODE]
            ?.let { runCatching { ThemeMode.valueOf(it) }.getOrNull() }
            ?: ThemeMode.System,
        hapticsEnabled = this[KEY_HAPTICS] ?: true,
        soundEnabled = this[KEY_SOUND] ?: false,
    )

    private companion object {
        val KEY_THEME_MODE = stringPreferencesKey("theme_mode")
        val KEY_HAPTICS = booleanPreferencesKey("haptics_enabled")
        val KEY_SOUND = booleanPreferencesKey("sound_enabled")
    }
}
```

Per greenfield spec 5.5 silent-best-effort: read errors return `emptyPreferences()` → defaults. Write errors propagate (DataStore's `edit` throws on IO; the caller's `viewModelScope.launch` will catch and log). The `runCatching` on `ThemeMode.valueOf` defends against a corrupt enum string (e.g. someone renamed an enum value in a future version — graceful fallback to System).

```kotlin
package dev.gaddal.sifr.feature.settings.ui

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import dev.gaddal.sifr.core.data.settings.SettingsRepository
import kotlinx.coroutines.channels.Channel
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.receiveAsFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

class SettingsViewModel(
    private val repository: SettingsRepository,
) : ViewModel() {

    private val _state = MutableStateFlow(SettingsState())
    val state: StateFlow<SettingsState> = _state.asStateFlow()

    private val _events = Channel<SettingsEvent>()
    val events = _events.receiveAsFlow()

    init {
        viewModelScope.launch {
            repository.observe().collect { settings ->
                _state.update { it.copy(settings = settings, isLoading = false) }
            }
        }
    }

    fun onAction(action: SettingsAction) {
        when (action) {
            is SettingsAction.SetThemeMode -> updateSettings { copy(themeMode = action.mode) }
            SettingsAction.ToggleHaptics -> updateSettings { copy(hapticsEnabled = !hapticsEnabled) }
            SettingsAction.ToggleSound -> updateSettings { copy(soundEnabled = !soundEnabled) }
            SettingsAction.BackClicked -> viewModelScope.launch { _events.send(SettingsEvent.NavigateBack) }
        }
    }

    private fun updateSettings(transform: dev.gaddal.sifr.core.domain.settings.AppSettings.() -> dev.gaddal.sifr.core.domain.settings.AppSettings) {
        viewModelScope.launch { repository.update(transform) }
    }
}
```

### 2.10 `core/ui/util/ObserveAsEvents.kt` (NEW)

```kotlin
package dev.gaddal.sifr.core.ui.util

import androidx.compose.runtime.Composable
import androidx.compose.ui.platform.LocalLifecycleOwner
import androidx.lifecycle.Lifecycle
import androidx.lifecycle.compose.LocalLifecycleOwner
import androidx.lifecycle.repeatOnLifecycle
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flowWithLifecycle
import kotlinx.coroutines.withContext

@Composable
fun <T> ObserveAsEvents(events: Flow<T>, onEvent: (T) -> Unit) {
    val lifecycleOwner = LocalLifecycleOwner.current
    androidx.compose.runtime.LaunchedEffect(events, lifecycleOwner.lifecycle) {
        lifecycleOwner.lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
            withContext(Dispatchers.Main.immediate) {
                events.collect(onEvent)
            }
        }
    }
}
```

The `repeatOnLifecycle(STARTED)` + `Dispatchers.Main.immediate` pattern guarantees: events only collected while screen is visible; UI updates run on the same dispatcher as Compose recomposition (no race between event handler and Compose state update).
