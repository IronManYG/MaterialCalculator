# Phase 2.4 — History feature

**Date:** 2026-05-10
**Status:** Ready for execution
**Branch:** `feature/phase2.4-history` off `development`
**Parent spec:** `docs/superpowers/specs/2026-05-09-greenfield-design.md` (sections 3.3, 4.4–4.6)

---

## 1. Goal

Add a Calculation History screen plus the cross-feature seam that lets the
Calculator write entries on every successful `=` and lets the user tap a past
result to restore it as the current expression. Establish Room as the project's
relational store. Land the `core/data/database/AppDatabase` aggregator that
later features (favourites, custom formulas) will extend.

This is the first phase that introduces a cross-feature data dependency: the
Calculator feature reads/writes through the `HistoryRepository` interface in
`core/`, but never imports any class from `feature/history/`. Boundary rule 1
of the greenfield spec stays intact.

## 2. Scope

### In scope

- Room 2.8.4 + KSP 2.3.7 (KSP plugin, no kapt — we're greenfield-aligned).
- `core/domain/history/HistoryEntry` pure-Kotlin domain model.
- `core/data/history/HistoryRepository` interface (cross-feature contract).
- `core/data/database/AppDatabase` (Room) aggregating all feature DAOs — per
  greenfield spec §2.2 boundary-rule exception.
- `feature/history/data/`: `HistoryEntity`, `HistoryDao`, `HistoryMappers`,
  `HistoryRepositoryImpl`.
- `feature/history/ui/`: full MVI cycle (State/Action/Event/VM/Root/Screen) +
  `components/HistoryItem`. Empty state. Clear-all confirmation dialog.
- Cross-feature seam:
  - `CalculatorViewModel` injects `HistoryRepository` and writes an entry on
    every successful `Calculate` (`Result.isFinite()`).
  - `CalculatorInputBus` (Koin singleton) carries one-shot expression strings
    from History back to Calculator. Calculator's VM collects and dispatches a
    `RestoreExpression` action.
- Calculator UI: history `IconButton` next to the existing settings button.
- Navigation 3: `HistoryRoute` `@Serializable data object : NavKey` + entry in
  `NavRoot`. Standard `dropUnlessResumed` wrapping.
- Strings (en + ar) for every new user-visible label. MissingTranslation is
  fatal in this project — both locales land in the same commit.

### Out of scope (deferred)

- Pagination of the history list. With a calculator that emits one row per
  `=` press, even heavy users won't exceed a few thousand rows; the spec's
  reactive `Flow<List<HistoryEntry>>` is fine until then.
- `HistoryViewModelTest`, `HistoryRepositoryImplTest` — same test-light
  deferral as Phase 2.3. Add when we revisit testing strategy holistically.
- Search / filter over history.
- Long-press multi-select delete.
- Pin / favourite individual history entries.
- Export / share history.
- `kotlinx-datetime`. Timestamps are stored as `Long` epoch-millis; the UI
  layer formats with `DateFormat.getDateTimeInstance(...)` against
  `Locale.getDefault()`. Avoids pulling in a 6 MB multiplatform datetime
  library for a single timestamp column.

### 3.2 Domain model

```kotlin
// core/domain/history/HistoryEntry.kt
package dev.gaddal.sifr.core.domain.history

data class HistoryEntry(
    val id: Long,
    val expression: String,
    val result: String,
    val timestampMs: Long,
)
```

`Long` (not `Instant`) — keeps `core/domain/` Android-free without pulling in
`kotlinx-datetime`. UI formats locally.

### 3.3 Repository contract

```kotlin
// core/data/history/HistoryRepository.kt
interface HistoryRepository {
    fun observe(): Flow<List<HistoryEntry>>
    suspend fun add(expression: String, result: String)
    suspend fun delete(id: Long)
    suspend fun clear()
}
```

`add(...)` takes the raw values rather than a fully-formed `HistoryEntry`
because callers don't know `id` or `timestampMs` — the repository owns both.

### 3.4 Room schema

```kotlin
// feature/history/data/HistoryEntity.kt
@Entity(tableName = "history")
data class HistoryEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0L,
    val expression: String,
    val result: String,
    val timestampMs: Long,
)

// feature/history/data/HistoryDao.kt
@Dao
interface HistoryDao {
    @Query("SELECT * FROM history ORDER BY timestampMs DESC")
    fun observe(): Flow<List<HistoryEntity>>

    @Insert
    suspend fun insert(entity: HistoryEntity): Long

    @Query("DELETE FROM history WHERE id = :id")
    suspend fun delete(id: Long)

    @Query("DELETE FROM history")
    suspend fun clear()
}

// core/data/database/AppDatabase.kt
@Database(entities = [HistoryEntity::class], version = 1, exportSchema = true)
abstract class AppDatabase : RoomDatabase() {
    abstract fun historyDao(): HistoryDao
}
```

`exportSchema = true` and Room schema goes to `app/schemas/`. Locks the v1
schema before first ship — future migrations diff against it.

**Locked on first ship:**

- DB file name: `sifr.db`
- Table name: `history`
- Column names: `id`, `expression`, `result`, `timestampMs`

### 3.5 Cross-feature seam

The greenfield spec §4.6 sketched a `SavedStateHandle("pending_expression")`
approach. That assumed `CalculatorViewModel.init` re-fires when navigating back
from History — it doesn't, because Nav3 keeps the Calculator entry alive
underneath the History entry. So `init` only fires once, when the app first
starts.

Replacement: a tiny one-shot `Channel`-backed bus, scoped as a Koin
singleton for the application's lifetime:

```kotlin
// core/data/calculator/CalculatorInputBus.kt
class CalculatorInputBus {
    private val _events = Channel<String>(capacity = Channel.BUFFERED)
    val events: Flow<String> = _events.receiveAsFlow()
    suspend fun emit(expression: String) = _events.send(expression)
}
```

- `HistoryViewModel.onAction(EntryClicked(entry))` → `bus.emit(entry.result)`
  → `_events.send(NavigateBack)`.
- `CalculatorViewModel.init` → `viewModelScope.launch { bus.events.collect { ... } }`
  — dispatches `CalculatorAction.RestoreExpression(expression)`.
- `ExpressionWriter.processAction` gains a new branch: `RestoreExpression` →
  `expression = action.value`.

Process-death note: if the process dies while History is on top, the bus loses
its (already-collected, transient) state. That matches the calculator's
existing behaviour — `ExpressionWriter.expression` doesn't survive process
death today either. No regression.

### 3.6 Writing on Calculate

`CalculatorViewModel` already routes every action through `ExpressionWriter`.
On a `Calculate` action:

1. Capture `pre = writer.expression` before calling `processAction(Calculate)`.
2. Call `processAction(Calculate)` (mutates `writer.expression` to result or
   `"Error"`).
3. If `writer.expression != "Error"` *and* `pre.isNotBlank()` *and*
   `pre != writer.expression`, fire-and-forget `historyRepo.add(pre, writer.expression)`.
   - Skip the no-op case (`pre == writer.expression`) so pressing `=` on a bare
     number doesn't pollute history.
   - Skip `Error` outcomes — meaningless to restore later.

`pre.isNotBlank()` blocks the `prepareForCalculation()` "0" fallback from
producing a `"" → "0"` history entry.

  pile of correctness traps. Use the per-item delete icon button instead; ship
  swipe later if the UX warrants.

## 6. Risk & rollback

- **Schema export folder** — `app/schemas/` is the locked v1 schema. Any field
  rename without a migration breaks every installed app. We're shipping `id`,
  `expression`, `result`, `timestampMs` and locking them.
- **`CalculatorInputBus` capacity** — `Channel.BUFFERED` (default 64). User
  would have to tap 65 history entries before any drop — rounding error.
- **Calc-on-Error idempotency** — pressing `=` while in Error state currently
  stays Error (covered by existing tests). The new history-write logic gates
  on `writer.expression != "Error"` so this case writes nothing.
- **Rollback** — single feature branch, single PR. If Phase 2.4 breaks any
  Phase 2.3 surface in review, we close the PR; `development` stays clean.
