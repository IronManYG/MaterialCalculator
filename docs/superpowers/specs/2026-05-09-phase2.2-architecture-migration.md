# Phase 2.2 — Architecture Migration

**Date:** 2026-05-09
**Status:** Draft for review
**Phase:** Phase 2.2 (post-namespace-rename, pre-feature-additions)
**Parent spec:** `docs/superpowers/specs/2026-05-09-greenfield-design.md` (sections 2 + 7)
**Branch family:** `feature/phase2.2{a,b,c,d}-*` (off `development`, one per sub-phase)

## 1. Context & Goals

Phase 2.0 modernized the build (Kotlin DSL + version catalog + Gradle 9.5 + AGP 9.2.1 + JDK 21). Phase 2.1 renamed the namespace to `dev.gaddal.sifr` and the user-visible label to **Sifr (صفر)**. Phase 2.2 does the **architectural reorganization** that makes settings + history + i18n (Phases 2.3 / 2.4 / 2.5) feasible.

**The greenfield spec already specifies the target architecture** (sections 2.1, 4, 5 of `2026-05-09-greenfield-design.md`). Phase 2.2 does not re-design — it executes the move, in slices small enough to land cleanly.

### Why split Phase 2.2 into sub-phases

The greenfield spec section 8 lists "Architecture migration" as a single Phase 2.2. In practice that bundles four largely-independent transforms:

1. **Package restructure** (move files into `core/` + `feature/calculator/`) — pure mechanical, no new deps.
2. **MVI refactor** (introduce `State` / `Event`, split `Root` from `Screen`, add `MainDispatcherRule` test infra).
3. **Koin DI** (add Koin, modules per layer, `koinViewModel()` in composables).
4. **Navigation 3** (add Nav3 deps, `NavRoot`, `Routes`, wire `MainActivity`).

Bundling them into one PR would produce a 600+ line diff that mixes "where files live" with "how state flows" with "what creates the ViewModel" — three very different review concerns. Splitting makes each PR readable, rollback-able, and lets us defer 2.2c/d if a Phase 2.3 settings prototype reshapes the DI/nav requirements.

### Scope of Phase 2.2 (the umbrella)

After all four sub-phases land, the codebase looks like greenfield spec section 2.1 — **for the calculator only**. Settings and history come later (Phases 2.3 / 2.4) and bring their own packages then. Stub directories or empty packages are NOT created in Phase 2.2.

### Out of scope (deferred)

- Settings feature (Phase 2.3)
- History feature (Phase 2.4)
- `Result<D, E>` + `CalcError` typing + `UiText` (Phase 2.5)
- Theme renames (`SifrTheme` → `AppTheme` per greenfield spec) — keep `SifrTheme` for now; rename can ride with theme expansion in a later phase
- Tests for `CalculatorViewModel` — added in 2.2b alongside the MVI refactor that makes them tractable

## 2. Sub-phase decomposition

| Sub-phase | Branch | Scope | Risk | Approx commits |
|---|---|---|---|---:|
| 2.2a | `feature/phase2.2a-package-restructure` | File moves + package decl/import rewrites only. No behavior change. | Low (compile-time only) | 7–9 |
| 2.2b | `feature/phase2.2b-mvi-refactor` | Introduce `CalculatorState`, `CalculatorEvent`, split `CalculatorScreen` → `CalculatorRoot` + `CalculatorScreen`, port to `StateFlow`, add `ObserveAsEvents`, add VM tests with Turbine + fakes. | Medium (state plumbing) | 5–7 |
| 2.2c | `feature/phase2.2c-koin-di` | Add Koin deps, `App.kt` Application class, `calculatorModule`, `appModule`, switch composables to `koinViewModel()`. | Low–Medium (DI graph wiring) | 3–4 |
| 2.2d | `feature/phase2.2d-navigation3` | Add Navigation 3 deps, `Routes.kt`, `NavRoot.kt`, wire `MainActivity` to host `NavRoot`. Calculator is the only destination at this point — Nav3 is wired without a real second screen. | Medium (new dep, Compose-host change) | 3–4 |

Each sub-phase is its own PR `feature/phase2.2X-* → development`. None of them touches `staging` or `master` — those branches remain on the Phase 2.1 cut until a release-worthy slice is ready (likely after 2.3 or 2.4).

### Why this order

- **2.2a first** unblocks everything else: MVI/Koin/Nav3 each touch the same files, so doing the moves first removes a major source of merge churn.
- **2.2b before 2.2c/d** because the `Root`/`Screen` split is what makes Koin's `koinViewModel()` and Nav3's `entryProvider` natural to wire — doing DI/nav before MVI means redoing the wiring afterward.
- **2.2c before 2.2d** because Nav3's `NavRoot` is the natural place to host top-level Koin scope; reversing this order means `MainActivity` temporarily owns a hand-instantiated VM that gets replaced again in 2.2d.

A user looking for a single shippable Phase 2.2 milestone should think of all four sub-phases together; this spec splits them only for execution hygiene.

### 3.2 Edit pattern per file

For each moved file:

1. **Move** the file under the new directory tree (creates intermediate dirs as needed).
2. **Rewrite** the top-line `package` declaration to the new path.
3. **Rewrite** any `import dev.gaddal.sifr.{domain,presentation,ui.theme}.*` to the new package.
4. Leave **all other content unchanged.** No logic changes, no rename, no comment additions.

### 3.5 Branching & PR

- **Branch:** `feature/phase2.2a-package-restructure` (off `development`).

## 4. What 2.2b–d will deliver (preview)

This section is a directional summary so the user knows what's coming. Each sub-phase will get its own spec at the time.

- **2.2b — MVI refactor.** Move `CalculatorViewModel` to expose `StateFlow<CalculatorState>` and `Channel<CalculatorEvent>` instead of `mutableStateOf<String>`. Split `CalculatorScreen` into `CalculatorRoot` (state + event collector) + `CalculatorScreen` (pure renderer of state). Add `core/ui/util/ObserveAsEvents.kt`. Add `MainDispatcherRule` and `CalculatorViewModelTest` (Turbine + fakes for any future repos; no repos exist yet so VM test is small).
- **2.2c — Koin DI.** Add Koin (latest stable via `dependency-version-lookup`). Add `App : Application` class wired in manifest. Add `feature/calculator/di/calculatorModule.kt` providing `CalculatorViewModel`. Add `di/appModule.kt` aggregating modules. Switch `CalculatorRoot`'s `viewModel()` call to `koinViewModel()`.
- **2.2d — Navigation 3.** Add `androidx.navigation3:*` (latest stable). Add `navigation/Routes.kt` (single `data object CalculatorRoute : NavKey`). Add `navigation/NavRoot.kt` with `NavDisplay` + `entryProvider`. Wire `MainActivity` to host `NavRoot()` instead of `CalculatorScreen()` directly. Calculator is the only destination — Nav3 is in place ready for Phase 2.3 to add `SettingsRoute`.
