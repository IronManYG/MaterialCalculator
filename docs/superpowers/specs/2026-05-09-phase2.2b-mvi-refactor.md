## 1. Context & Goals

Phase 2.2a moved files into `core/` + `feature/calculator/`. Phase 2.2b changes the **shape** of presentation state and the composable hierarchy to match the project MVI convention (`android-presentation-mvi` skill).

### What changes (in narrative form)

Today, `CalculatorViewModel` exposes a single `var expression: String by mutableStateOf("")`. The composable reads `viewModel.expression` directly. There is no `State` class, no `StateFlow`, no `Root`/`Screen` split, and no test infrastructure to exercise the ViewModel.

After this phase, `CalculatorViewModel` will:

- Hold a `MutableStateFlow<CalculatorState>` and expose it as `StateFlow<CalculatorState>`.
- Update state through `_state.update { it.copy(...) }`.
- Process `CalculatorAction` via `onAction` (already exists).
- NOT expose any `Channel<CalculatorEvent>` yet — we have no events to emit (no navigation, no snackbar). The Event surface lands in Phase 2.3 when settings navigation creates the first real event. **YAGNI: no empty event scaffolding.**

The composable layer will:

- `CalculatorRoot(viewModel = viewModel())` — collects state with `collectAsStateWithLifecycle()`, passes `state` and `viewModel::onAction` down.
- `CalculatorScreen(state, onAction)` — pure renderer of state, previewable.
- `MainActivity` calls `CalculatorRoot()` instead of `CalculatorScreen()` directly.
- Both Root and Screen live in the same file (`CalculatorScreen.kt`) per skill convention.

Test infrastructure lands:

- `MainDispatcherRule` — JUnit4 rule installing `UnconfinedTestDispatcher()` as `Dispatchers.Main` for ViewModel tests.
- `CalculatorViewModelTest` — 3–4 tests covering the state-flow contract (state starts empty, digit appends, Calculate evaluates, Calculate-on-error stays Error).
- New deps: `kotlinx-coroutines-test 1.11.0`, `turbine 1.2.1`.

### Out of scope (explicitly deferred)

- **`CalculatorEvent` channel** — deferred to Phase 2.3 (first real event is navigation to settings).
- **`ObserveAsEvents` utility** — deferred to Phase 2.3 (lands with the first event).
- **Koin DI** — Phase 2.2c. `CalculatorRoot` keeps `viewModel = viewModel()` until then.
- **Navigation 3** — Phase 2.2d.
- **Process death / `SavedStateHandle`** — deferred. Per skill: "Only save what truly matters after process death." A scratch calculator expression is not user-critical input; existing behavior (no saved state) is acceptable for this phase. Revisit if user testing flags it.
- **`UiText` for error mapping** — deferred to Phase 2.5 (typed errors). The `expression == "Error"` sentinel pattern stays for now.
- **JUnit5 / AssertK migration** — deferred indefinitely; greenfield spec lists them as separate improvements. This phase keeps JUnit4 + Truth to minimize surface area of change.
- **Renaming `CalculatorAction.Number/Op/Clear/...`** — names stay as-is. The action surface already matches the MVI convention; no change needed.

### Why YAGNI on events for one phase

The `android-presentation-mvi` skill describes the full triple State + Action + Event. Adding an empty `sealed interface CalculatorEvent` plus a `Channel<CalculatorEvent>` plus an `ObserveAsEvents` utility "to establish the pattern" violates the project rule "Don't design for hypothetical future requirements." The first real event arrives in Phase 2.3 (NavigateToSettings) — adding the wiring then is a single small commit, not a re-architect.

### 2.2 `feature/calculator/ui/CalculatorViewModel.kt` (REWRITE)

```kotlin
package dev.gaddal.sifr.feature.calculator.ui

import androidx.lifecycle.ViewModel
import dev.gaddal.sifr.feature.calculator.domain.CalculatorAction
import dev.gaddal.sifr.feature.calculator.domain.ExpressionWriter
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update

class CalculatorViewModel(
    private val writer: ExpressionWriter = ExpressionWriter(),
) : ViewModel() {

    private val _state = MutableStateFlow(CalculatorState())
    val state: StateFlow<CalculatorState> = _state.asStateFlow()

    fun onAction(action: CalculatorAction) {
        writer.processAction(action)
        _state.update { it.copy(expression = writer.expression) }
    }
}
```

Notes:
- `writer.processAction(...)` is synchronous CPU work — no `viewModelScope.launch` needed (per the greenfield spec §4.7 dispatcher discipline).
- `ExpressionWriter` keeps its mutable `expression` field. Future refactor could make `ExpressionWriter` pure, but not in this phase.
- Default-arg constructor is preserved (`writer = ExpressionWriter()`) so the no-arg `viewModel()` factory still works until 2.2c brings Koin.

### 2.3 `feature/calculator/ui/CalculatorScreen.kt` (SPLIT into Root + Screen)

                        RoundedCornerShape(
                            bottomStart = 25.dp,
                            bottomEnd = 25.dp

                    .background(MaterialTheme.colorScheme.secondaryContainer)
                    .padding(
                        vertical = 64.dp,
                        horizontal = 16.dp

                actions = calculatorActions,

        }

### 2.7 `core/ui/util/MainDispatcherRule.kt` (NEW)

```kotlin
package dev.gaddal.sifr.core.ui.util

import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.test.TestDispatcher
import kotlinx.coroutines.test.UnconfinedTestDispatcher
import kotlinx.coroutines.test.resetMain
import kotlinx.coroutines.test.setMain
import org.junit.rules.TestWatcher
import org.junit.runner.Description

@OptIn(ExperimentalCoroutinesApi::class)
class MainDispatcherRule(
    val testDispatcher: TestDispatcher = UnconfinedTestDispatcher(),
) : TestWatcher() {
    override fun starting(description: Description) {
        Dispatchers.setMain(testDispatcher)
    }

    override fun finished(description: Description) {
        Dispatchers.resetMain()
    }
}
```

**Why `core/ui/util/` and not `app/src/test/`:** Future ViewModel tests in `feature/settings/`, `feature/history/` etc. all need this rule. Promoting it to `core/ui/util/` immediately matches the greenfield spec section 2.1 layout and avoids a later move.

But there's a subtlety: `MainDispatcherRule` depends on JUnit4 + kotlinx-coroutines-test, which are `testImplementation`-only. Putting it in `main/` would force production code to depend on test libraries. Compromise: place it under `app/src/test/java/dev/gaddal/sifr/core/ui/util/` for now — same package as the production target, but lives in the test source set so it has access to test dependencies. When future feature modules need it (Phase 2.3 onwards), it stays in `test/` and is shared via the same package — Kotlin doesn't enforce one-source-set-per-package.

### 2.8 `feature/calculator/ui/CalculatorViewModelTest.kt` (NEW)

```kotlin
package dev.gaddal.sifr.feature.calculator.ui

import app.cash.turbine.test
import com.google.common.truth.Truth.assertThat
import dev.gaddal.sifr.core.ui.util.MainDispatcherRule
import dev.gaddal.sifr.feature.calculator.domain.CalculatorAction
import dev.gaddal.sifr.feature.calculator.domain.Operation
import kotlinx.coroutines.test.runTest
import org.junit.Rule
import org.junit.Test

class CalculatorViewModelTest {

    @get:Rule
    val mainDispatcherRule = MainDispatcherRule()

    @Test
    fun `Initial state has empty expression`() = runTest {
        val viewModel = CalculatorViewModel()

        viewModel.state.test {
            assertThat(awaitItem().expression).isEqualTo("")
        }
    }

    @Test
    fun `Number action appends digit to expression`() = runTest {
        val viewModel = CalculatorViewModel()

        viewModel.onAction(CalculatorAction.Number(5))

        assertThat(viewModel.state.value.expression).isEqualTo("5")
    }

    @Test
    fun `Calculate produces result`() = runTest {
        val viewModel = CalculatorViewModel()

        viewModel.onAction(CalculatorAction.Number(2))
        viewModel.onAction(CalculatorAction.Op(Operation.ADD))
        viewModel.onAction(CalculatorAction.Number(3))
        viewModel.onAction(CalculatorAction.Calculate)

        assertThat(viewModel.state.value.expression).isEqualTo("5")
    }

    @Test
    fun `Calculate while in Error state stays Error`() = runTest {
        val viewModel = CalculatorViewModel()

        // Trigger Error state via division by zero
        viewModel.onAction(CalculatorAction.Number(5))
        viewModel.onAction(CalculatorAction.Op(Operation.DIVIDE))
        viewModel.onAction(CalculatorAction.Number(0))
        viewModel.onAction(CalculatorAction.Calculate)
        assertThat(viewModel.state.value.expression).isEqualTo("Error")

        // Pressing = again should not crash and should remain in Error state
        viewModel.onAction(CalculatorAction.Calculate)

        assertThat(viewModel.state.value.expression).isEqualTo("Error")
    }
}
```

The fourth test closes the reviewer-flagged backlog item "One-liner test: Calculate on Error stays Error" (per `project_phase2_backlog.md`). Worth claiming the win as part of this phase since the test infra is already being added.
